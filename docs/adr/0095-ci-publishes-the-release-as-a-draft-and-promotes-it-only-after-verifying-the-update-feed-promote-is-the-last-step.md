# CI publishes the release as a draft and promotes it only after verifying the update feed; promote is the last step

- Status: Accepted
- Date: 2026-08-28

## Context

`.github/workflows/release.yml` is now the authoritative publisher for Sound Buddy
(scripts/release.sh is being reduced to a local fallback). Until this change CI handed
`softprops/action-gh-release` a non-draft release immediately after the build, with no
gate between the two. `latest-mac.yml` — electron-updater's feed — is generated by
electron-builder alongside the artifacts, and a mismatch in it (a filename GitHub
rewrites, a stale sha512, a wrong size) makes every installed app's update check fail
with a signature error. scripts/release.sh has guarded against exactly this since #1226
via the shared `parseLatestMacYml` + `checkUpdateFeed` pair, and stages a draft it
promotes last (#623/#645); CI had neither, so the safest publisher was the one we were
moving away from. GitHub makes `releases/latest` and the download URLs live the instant
a release is non-draft, so any verification that happens after publish is too late.

## Decision

The release workflow publishes as a draft (`draft: true` on
`softprops/action-gh-release`) and becomes public only through a final
`gh api -X PATCH repos/on-par/sound-buddy-releases/releases/$RELEASE_ID -F draft=false`
step. Between the build and the publish, an unconditional step runs
`node scripts/ci-update-feed.mjs`, which hashes the artifacts in `app/release` and runs
them through the same shared `parseLatestMacYml`/`checkUpdateFeed` functions
scripts/release.sh uses, failing the job on any mismatch. The promote step is the last
step in the job — the `if: always()` temporary-keychain cleanup is ordered above it, not
below — so promote inherits the implicit `success()` gate and cannot run when any earlier
step, verification included, failed. `auditReleaseWorkflow` in
packages/shared/src/release-workflow.ts enforces all of this as text rules over the
workflow file, and the existing "the real release.yml passes the audit" test makes a
regression fail `npm test` rather than a release.

## Consequences

Positive: no artifact set can reach buyers with a feed that does not describe it; a bad
build strands a private draft instead of breaking auto-update; the ordering is checked by
the unit suite on every PR, not by reviewer memory; CI and scripts/release.sh now share
one verification implementation, so the two publishers cannot drift.
Negative: a release that fails after the draft is created needs a human to delete or
promote the stranded draft (the promote step's failure message prints the exact command);
the promote step depends on the publish action's `id` output, an external contract we
guard with an explicit empty-id check rather than trust silently; and any future step
added to the release job must be inserted above promote or the audit fails.
